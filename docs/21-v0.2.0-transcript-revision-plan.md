# v0.2.0 Transcript Revision Plan

Status: implemented and acceptance-audited on `main`; release packaging remains.

This document consolidates the design decisions for manual transcript revision. It is an
implementation plan and cross-document summary. Normative behavior is specified in
[13 - Transcript revisions](13-transcript-revisions.md), the CLI contract, requirements,
and ADR-0020.

## 1. Goal

Version `0.2.0` adds a revision layer between immutable ASR results and derived exports.
The primary workflow is manual correction of Polish transcripts in an ordinary external
text editor. The same application-layer contracts must later support automated LLM
correction and a GUI without creating independent correction paths.

The first manually corrected corpus is expected to contain 24 podcast episodes. It will
serve as ground truth for later correction benchmarks. Manual translation will similarly
serve as the baseline for a later translation pipeline, but translation is not part of
`0.2.0`.

## 2. Core invariants

1. `results.json` remains immutable and is never edited by correction workflows.
2. A revision is a separate immutable, schema-valid JSON artifact.
3. Every revision is a complete snapshot of the corrected transcript, not a delta or a
   replayable patch stream.
4. A revision is linked to the exact base result by SHA-256 and result identity.
5. A revision may identify a parent revision for provenance, but the parent is not needed
   to render the child revision.
6. Corrected text maps back to stable canonical `word_id` anchors.
7. Normal correction does not edit canonical timestamps. Timing is inherited from the
   mapped source words by `EffectiveTranscript`.
8. Text punctuation remains part of text tokens; punctuation is not a separate word
   structure.
9. Sentence boundaries are inferred from corrected punctuation. Reviewers do not maintain
   a separate sentence-boundary data structure.
10. Meaningful repetitions and self-corrections are preserved unless the reviewer
    explicitly changes them.
11. Speaker attribution may be corrected by reassigning corrected text to an existing
    canonical `speaker_id`.
12. TXT, SRT, VTT, and segments JSON are regenerated from one selected effective
    transcript. Independent hand-edited exports are not supported.
13. The revision core is interface-independent. CLI, future GUI, and future LLM providers
    call the same application services and alignment logic.
14. `EffectiveTranscript` is a runtime view, not another persisted source-of-truth file.

## 3. v0.2.0 scope

The release target includes:

- `EWP-REVIEW 1`, a human-readable, versioned text interchange format;
- single-file and batch `revise prepare`;
- single-file and batch `revise apply`;
- `revise preview`, equivalent to applying with `--no-apply`;
- `revise edit`, which opens an external editor and applies after a successful editor exit
  unless `--no-apply` is supplied;
- anchored text alignment supporting ordinary substitutions, punctuation changes,
  sentence-boundary changes, merge/split cases, insertions, deletions, and speaker
  reassignment;
- immutable full-snapshot `revision_NNN.json` artifacts;
- mandatory provenance, alignment metadata, summary statistics, and warnings;
- optional detailed audit output through `--audit`;
- reconstruction of a detailed audit from the base result and revision artifacts;
- revision-aware `transcriber export` using `--revision none|latest|PATH`;
- an `EffectiveTranscript` runtime abstraction shared by raw and revised exports;
- model-free operation: no source audio, ASR, alignment model, diarization model, or GPU is
  needed to prepare/apply revisions or export a revision.

## 4. Explicit non-goals for v0.2.0

The following are deliberately outside this increment:

- LLM correction;
- LLM chunking implementation;
- translation;
- automated translation;
- GUI;
- glossary/dictionary implementation;
- manual word-timestamp editing;
- audio-based re-alignment after correction;
- automatic removal of repetitions or fillers;
- a separate persisted sentence model maintained by reviewers;
- patch-only or event-sourced revisions.

The schemas and services should not prevent these later features.

## 5. End-to-end manual workflow

```text
                         source audio
                              |
                              v
                   ASR + word alignment
                              |
                              v
                    immutable results.json
                              |
                 transcriber revise prepare
                              |
                              v
                       *.review.txt
                              |
                      external editor
                              |
                              v
                  transcriber revise apply
                              |
                parse + align + validate
                              |
                              v
                  *_revision_NNN.json
                              |
                       RevisionResolver
                              |
                              v
                     EffectiveTranscript
                         /     |     \
                        v      v      v
                       TXT    SRT    VTT
                              |
                       segments JSON
```

No step after creation of `results.json` requires reopening audio for normal correction.

## 6. Batch workflow

Directory input is a first-class requirement rather than a later wrapper around a
single-file API.

Example:

```text
transcriber revise prepare ./output-ewp-transcripts/
```

prepares review files for all matching completed results directly in that directory.
Subdirectories are ignored unless `--recursive` is explicitly enabled.

A typical batch flow is:

```text
transcriber revise prepare ./output-ewp-transcripts/ --output-dir ./review/
# edit review files over time
transcriber revise apply ./review/ --results-dir ./output-ewp-transcripts/
```

Batch discovery must use deterministic natural ordering. One failed item must not stop
remaining items when the existing runtime batch policy allows continuation. A mixed
success/failure batch returns the existing batch-failure exit code.

## 7. CLI target

```text
transcriber revise prepare INPUT [OPTIONS]
transcriber revise apply INPUT [OPTIONS]
transcriber revise preview INPUT [OPTIONS]
transcriber revise edit INPUT [OPTIONS]
transcriber revise audit REVISION [OPTIONS]
```

`INPUT` for `prepare` is a completed results file or a directory containing completed
results. The initial v0.2.0 implementation prepares raw canonical results. The format and
revision schema are already compatible with preparing a future parent revision.

`INPUT` for `apply` and `preview` is an `EWP-REVIEW 1` file or a directory containing
review files.

### 7.1 Preview semantics

These two forms are semantically equivalent:

```text
transcriber revise preview episode.review.txt
transcriber revise apply episode.review.txt --no-apply
```

Both perform parsing, source verification, anchored alignment, validation, and change
summary generation. Neither writes a revision or derived export.

The equivalence must be documented in `--help` as well as the Markdown CLI specification.
Both commands must call the same application operation rather than duplicate alignment
logic.

### 7.2 External editor semantics

```text
transcriber revise edit episode_results.json
```

performs:

1. prepare a review file;
2. start the configured external editor and wait for it to exit;
3. if the editor exits successfully, apply the saved review file automatically;
4. validate and persist the new revision atomically.

Saving the file and closing an editor with exit status zero is therefore treated as
approval to create the revision. This behavior must be explicit in documentation and
`--help`.

```text
transcriber revise edit episode_results.json --no-apply
```

opens the editor but stops after it exits. The edited review remains available for later
preview or apply.

The implementation must execute the editor as an argument vector, not through
`shell=True`.

## 8. EWP-REVIEW 1 design

The review file is intentionally simple enough for VS Code, Vim, Kate, Notepad++, or any
other plain-text editor. It is not the source of truth. It is an editable interchange
artifact used to create a revision.

Example shape:

```text
# EWP-REVIEW 1
# job_id: episode10_mono
# base_result_file: episode10_mono_results.json
# base_result_sha256: <64 hex characters>
# base_result_schema_version: 1.0
# base_result_version: 1
# language: pl

@@ anchor word_000001..word_000068
@@ speaker speaker_001

Normal editable transcript text.
The generator may render one sentence per line for readability.

@@ speaker speaker_002
A short interjection can be reassigned by changing speaker directives.

@@ speaker speaker_001
The original speaker can then continue.

@@ anchor word_000069..word_000136
@@ speaker speaker_001
...
```

Rules:

- header metadata is machine-owned and must not be edited during normal review;
- anchors are machine-owned and define bounded source-word alignment windows;
- speaker directives are intentionally editable;
- ordinary line breaks are presentation only; sentence boundaries come from punctuation;
- punctuation remains part of normal text;
- anchors cover the base word timeline exactly once, in order;
- modified, missing, overlapping, duplicated, or out-of-order anchors are rejected;
- applying a review requires a base result whose exact bytes match
  `base_result_sha256`;
- a generated relative filename/path is only a resolution hint; SHA-256 is authoritative;
- the review format is UTF-8.

The formal grammar and validation rules are in `schemas/ewp-review.schema.md`.

## 9. Alignment behavior

The alignment implementation is internal and may evolve, but externally visible behavior
must remain deterministic for a fixed algorithm version.

Alignment is constrained independently within review anchors. This avoids a single global
alignment over a multi-hour transcript and reduces ambiguity around repeated phrases.

The aligner must support:

```text
1 source word  -> 1 corrected token    unchanged/substitution
N source words -> 1 corrected token    merge
1 source word  -> N corrected tokens   split
0 source words -> 1 corrected token    insertion
N source words -> 0 corrected tokens   deletion
```

Punctuation-only changes are text changes on an existing mapping rather than new
punctuation tokens.

Comparison may use normalized text for scoring, including Unicode normalization, case
normalization, and punctuation-insensitive comparison, but the exact reviewer text is
retained as output text.

The aligner must not silently collapse repetitions. If the source says `to to` and the
review retains `to to`, both occurrences remain. If a reviewer or future LLM changes it
to one occurrence, that is an explicit deletion.

When multiple equally plausible mappings remain after anchor constraints, the affected
item must be reported as ambiguous. v0.2.0 must not silently select an arbitrary mapping
that can change word timing or speaker attribution.

## 10. Timing policy

Manual timestamp editing is not part of the ordinary revision flow.

A corrected token receives timing from its source mapping at runtime:

- one-to-one: inherit that source word span;
- merge: use the envelope from the first mapped source word start to the last mapped
  source word end;
- split: all corrected tokens mapped to the same source word share one timing group;
- insertion: keep no invented canonical timestamp in the revision; attach the text to an
  adjacent effective timing group for subtitle planning;
- deletion: creates no effective token.

If an insertion occurs between source words separated by a long pause, the resolver must
emit a warning because either adjacent display choice may be visually awkward. The
initial proposed warning threshold is configurable and should start conservatively at
2000 ms until the larger corpus provides evidence for tuning.

A future emergency timing-override feature is backlog work and must not complicate the
normal v0.2.0 review format.

## 11. Speaker correction

Each persisted revision token has a corrected `speaker_id` that must refer to an existing
speaker in the base canonical result.

A reviewer changes attribution by moving a span under a different `@@ speaker` directive.
This directly addresses short interjections that diarization/ASR assigned to the
surrounding speaker.

Creating an entirely new speaker identity or renaming the canonical speaker registry is
not required for v0.2.0. Future GUI work may add a separate speaker-management operation.

## 12. Revision artifact

A revision is a complete corrected state. It does not require replaying earlier changes.

Required concepts:

- revision schema/application version;
- unique revision ID and sequential revision number;
- base result identity and SHA-256;
- optional parent revision identity and SHA-256;
- creation/provenance metadata;
- corrected transcript tokens;
- mapping from corrected tokens to zero, one, or many canonical `word_id` values;
- insertion anchors when no canonical source word exists;
- corrected speaker attribution;
- alignment strategy/version metadata;
- summary statistics;
- structured warnings.

The proposed machine-readable schema is `schemas/revision.schema.json`.

## 13. Revision lineage and benchmark branches

Revision numbering does not imply a single linear history.

The model supports both lineage:

```text
results
  -> revision_llm_001
       -> revision_manual_002
```

and sibling benchmark results:

```text
results
  -> manual gold revision
  -> model A revision
  -> model B revision
  -> model C revision
```

Every child is a full snapshot. `parent_revision` documents direct lineage when one
exists. A sibling can reference the same base result without referencing another sibling.

`--revision latest` means the highest allocated revision number whose base-result hash
matches the selected canonical result. Benchmark tooling should use explicit paths rather
than relying on `latest` when sibling meaning matters.

## 14. EffectiveTranscript

`EffectiveTranscript` is the central implementation boundary for v0.2.0.

Conceptually:

```text
CanonicalResult + no revision
            |
            v
       raw resolver
            |
            +-------------------+
                                v
                         EffectiveTranscript
                                ^
            +-------------------+
            |
CanonicalResult + Revision
            |
            v
     RevisionResolver
```

A minimal runtime token should expose fields equivalent to:

```text
text
speaker_id
source_word_ids
start_ms / end_ms when resolvable
timing group / timing provenance needed by subtitle planning
```

This type is not serialized as another authoritative JSON artifact.

Exporters should be refactored to consume `EffectiveTranscript` (or stable interfaces
backed by it) instead of reading `CanonicalSegment.text` in one exporter and
`CanonicalWord.text` in another. This removes the current dual-text source problem while
leaving the v0.1 canonical schema unchanged.

## 15. Export changes

`transcriber export` gains:

```text
--revision none
--revision latest
--revision PATH
```

Backward compatibility requirement:

- omitting `--revision` behaves like `--revision none`;
- raw export remains based on the unchanged canonical result;
- revision-aware export verifies that the selected revision references the exact base
  result SHA-256;
- export remains model-free and audio-free.

TXT sentence splitting runs on corrected text. A punctuation correction such as:

```text
No dobra wiesz co chyba tak.
```

becoming:

```text
No dobra. Wiesz co? Chyba tak.
```

must therefore regenerate the established one-sentence-per-line TXT layout without a
separate manually maintained sentence structure.

Subtitle generation uses corrected effective tokens and inherited timing while retaining
existing readability constraints.

Revision-aware derived filenames must remain non-destructive and include enough revision
identity to avoid confusing raw and corrected exports. A recommended convention is:

```text
<job_id>_transcript_revision_001.txt
<job_id>_subtitles_revision_001.srt
<job_id>_subtitles_revision_001.vtt
<job_id>_segments_revision_001.json
```

For a base canonical result with an existing `_vNNN` suffix, retain the base result version
before the revision suffix. Exact forced re-export suffix allocation should continue to
use the existing output-lock/version allocator rather than overwrite an existing file.

Batch revision-aware export is useful but is not a release-blocking v0.2.0 requirement
unless implementation falls naturally out of the revised export resolver.

## 16. Audit and provenance

Every revision always stores compact provenance and summary metadata. The detailed
change list is optional.

Always persisted:

- manual/LLM method;
- interface (`cli` now; future `gui`/`api`);
- creation time and application version;
- base result and optional parent hashes;
- alignment strategy/version;
- token counts;
- substitution, merge, split, insertion, deletion, punctuation-only change, speaker-change,
  ambiguity, and warning counts.

Optional:

```text
transcriber revise apply episode.review.txt --audit
```

writes a detailed audit artifact suitable for diagnostics and benchmarks.

A base-relative detailed audit must also be reconstructable later from immutable
`results.json` plus the full revision snapshot. A parent-relative audit can be reconstructed
when the parent revision artifact is also supplied or resolvable.

Audit is diagnostic evidence; it is not required to materialize a revision or export it.

## 17. Configuration

v0.2.0 adds a small `[revision]` section to the normal strict TOML configuration. Proposed
initial keys:

```toml
[revision]
anchor_target_words = 200
anchor_target_speaker_blocks = 5
long_gap_warning_ms = 2000
generate_audit = false
editor = ""
```

CLI flags override configuration through the existing precedence rules. Batch failure
behavior should reuse the existing runtime batch policy rather than introduce a duplicate
revision-only setting.

Future automated correction chunk settings must also be configuration-driven. Exact
defaults are deferred until the automated correction implementation and benchmark, but
the future contract requires a configurable target chunk size, hard maximum, and
read-only overlap. No model-specific context-window size may be hard-coded into the
revision engine.

## 18. Future automated correction

Automated correction follows manual correction and precedes translation in the roadmap.
It must use the same `RevisionEngine` and alignment rules.

Future data flow:

```text
CanonicalResult / EffectiveTranscript
              |
         chunk builder
              |
      local or cloud API LLM
              |
       corrected chunk text
              |
       same revision aligner
              |
        Revision snapshot
```

Chunks should be substantially larger than sentence fragments and sized for the selected
model. The exact size is configurable. Adjacent chunks have read-only context overlap:
only one chunk owns each editable source range, preventing two LLM calls from producing
conflicting corrections to the same words.

The LLM does not receive audio and does not generate authoritative timestamps. It receives
relevant text plus source word/speaker/timing metadata for context, while the local
revision engine performs mapping and validation.

Correction prompts must be transcription-conservative. The implemented
`faithful-correction-v11` contract narrows automated changes to obvious ASR lexical errors and
high-confidence proper-name spelling; it explicitly preserves capitalization, punctuation, and
sentence boundaries for manual review. The revision engine still supports human corrections to
all of those categories. Automated correction must preserve spoken repetitions, self-corrections,
fillers, malformed sentences, grammatical errors, and stylistic quirks. The goal is faithful
transcription, not edited prose. Each provider
response supplies corrected editable text. The local application derives the structured
change list (source span, before, after, and deterministic category), speaker mapping, and
authoritative audit. Optional provider annotations are advisory evidence only.

Cloud APIs must be explicit opt-in operations with separate privacy documentation. The
local-only v0.2.0 privacy contract is not weakened in advance.

## 19. Optional project-scoped dictionaries

A single global dictionary is explicitly not planned. Dictionary support is not part of
v0.2.0 and remains backlog work.

If later benchmarks show value, the program may support multiple small, named,
project-scoped dictionaries selected explicitly for one project or job, such as:

```text
podcast
training
history_lectures
```

A selected project dictionary may be sent as context to an LLM correction/translation
provider. No dictionary is automatically inherited across projects or applied globally.
Dictionary identity and content hash must be included in provenance whenever it affects
automated output. Using dictionary context in ASR is not planned by default because an
irrelevant vocabulary bias can reduce recognition quality. The feature remains backlog
work until benchmark evidence justifies it.

## 20. Translation compatibility backlog

Translation is a separate pipeline, not another operation inside transcript correction.
The v0.2.0 design must merely preserve compatibility with it.

Future translation sources may be:

```text
--source raw                     canonical transcript without correction
--revision PATH|latest           corrected transcript
```

A raw translation is intentionally a "dirty" translation path and remains useful for
experiments and quick outputs.

The future translation pipeline will:

- create sentence-level source units after sentenceization of the selected transcript;
- map translations by sentence rather than word because word counts and ordering differ
  between languages;
- inherit source sentence time spans for subtitle planning;
- persist a structured immutable translation artifact from which target TXT/SRT/VTT/HTML
  can be regenerated;
- support manual translation as the first benchmark baseline;
- later add LLM translation and manual revision of machine translations;
- reuse versioning, provenance, editor, batch, audit, and GUI infrastructure where useful,
  but use translation-specific sentence mapping rather than transcript word alignment.

The exact translation artifact schema is deliberately deferred until translation work
begins.

## 21. GUI compatibility

GUI remains near the end of the roadmap. v0.2.0 should not introduce GUI abstractions.
Instead it must provide application services that a GUI can call directly:

- prepare/editable transcript model;
- preview alignment without persistence;
- apply revision;
- resolve raw/revised effective transcript;
- export selected transcript;
- return structured warnings, diff summaries, and batch outcomes.

A GUI may hide review anchors because they are internal alignment metadata. It must not
implement a second correction model.

## 22. Suggested implementation sequence

1. Accept ADR-0020 and normative documentation.
2. Add `RevisionConfig` and default/example TOML keys.
3. Add revision domain models and JSON Schema.
4. Implement `EWP-REVIEW 1` parser/renderer and strict validation.
5. Implement deterministic anchored alignment and its unit tests.
6. Implement revision snapshot materialization, hashing, allocation, and atomic writes.
7. Implement `RevisionResolver` and `EffectiveTranscript`.
8. Refactor TXT/SRT/VTT/segments exporters to use the effective transcript path while
   preserving raw behavior.
9. Add `revise prepare`, `apply`, and `preview`, including batch behavior.
10. Add `revise edit` and editor lifecycle handling.
11. Add optional audit generation and audit reconstruction.
12. Add revision-aware export flags and help text.
13. Run unit/integration acceptance tests.
14. Manually correct the 24-episode baseline corpus and record workflow/alignment defects
    before starting LLM correction.

## 24. Release acceptance summary

v0.2.0 is ready when:

- raw v0.1 export behavior remains compatible;
- a review round-trip with no textual edits maps every token correctly;
- manual punctuation, proper-name, sentence-boundary, merge/split, insertion/deletion,
  repetition, and speaker-reassignment cases are covered;
- malformed or stale review anchors cannot silently create a revision;
- preview and `apply --no-apply` produce equivalent non-mutating outcomes;
- batch prepare/apply works deterministically and isolates failures;
- every revision is a full standalone snapshot linked to the exact base result hash;
- revision-aware TXT/SRT/VTT/segments export works without audio or ML models;
- provenance and summary statistics are always present;
- detailed audit is optional and can be reconstructed base-relative later;
- documentation and `--help` describe the external-editor apply behavior explicitly.
